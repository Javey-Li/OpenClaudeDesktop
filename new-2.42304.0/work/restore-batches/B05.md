## Instructions
1) New pure harness src/approval.js:
- `escalationModeOf(request)`: parse /escalate sandbox to ([\w-]+)/ from request.reason, else /with ([\w-]+) permissions/ from request.displayReason?.en; null if neither matches.
- `grantKeyFor({origin, toolName, item, mode})`:
  - ask: fileChange → 'ask:file'; commandExecution → `ask:command:${item.command}`; anything else → `ask:tool:${toolName}`.
  - escalation: `escalate:${mode}:command:${command}`; fileChange → `escalate:${mode}:file:${sorted change paths joined by '|'}`; other → `escalate:${mode}:tool:${toolName}`.
- `sessionGrantable({origin, mode, item})`: false when origin==='escalation' && mode==='danger-full-access' && item?.type==='fileChange'; true otherwise.
- `reasonFor(request, origin)`:
  - ask → null;
  - escalation → text = displayReason?.en ?? reason ?? null with /^Allow this operation with [\w-]+ permissions:\s*/ stripped, prefixed `Needs ${mode}: ` when mode is known.
  - Never use the zh text.
- `withinRoots(path, roots)`: path.resolve both sides; true when equal to a root or startsWith(root + path.sep). This rejects '../' traversal and sibling prefixes ('/a/bc' vs '/a/b').

2) index.js:
- LiveThread.askedCalls = new Set(). In the Ask-mode pre-execute hook, when it returns 'ask', add exec.callId.
- askClient:
  - origin = thread.askedCalls.delete(request.callId) ? 'ask' : 'escalation'; mode = escalationModeOf(request);
  - reason = reasonFor(request, origin);
  - grantKey = grantKeyFor(...);
  - remove the dead `tool:${toolName}` check.
  - If origin is escalation, the item is a fileChange, thread.permission.extraRoots is non-empty, and every change path (absolute) is withinRoots of the extraRoots: return 'allowed-once' without asking.
  - Add params.sessionGrantable = sessionGrantable(...). Codex clients ignore unknown fields.
  - acceptForSession stores the key only when it is grantable.
- applyPermissions:
  - when params.sandboxPolicy?.type === 'workspaceWrite', set thread.permission.extraRoots = await Promise.all(writableRoots minus cwd → realpath, falling back to the raw path);
  - when the effective preset target changes, delete every sessionGrants key starting with 'escalate:'.
- Batch 4 already rejects escalations in Plan mode before askClient; keep that.

3) App approval-card-model.mjs:
- When params.sessionGrantable === false, omit the acceptForSession action.
- Move params.reason into its own `reason` field of the model; it must not appear in the context list.
- Derive the heading from the item when one is found (main.jsx:2196 already passes it), following the source table at approval-current.js:14508-14595:
  - commandExecution with item.description → action 'run', meta description, detail the command (clampTitle);
  - dynamicToolCall tool 'subagent' or 'subagent_fork', or collabAgentToolCall tool 'spawnAgent' → 'run an agent', meta = arguments.description ?? first line of prompt, detail = pretty JSON of arguments;
  - dynamic 'skill' → 'run skill', meta `/${arguments.name}`;
  - webSearch openPage, or dynamic 'web_fetch' → 'fetch', meta url;
  - web_search → 'search the web';
  - mcpToolCall → `use ${tool} (${server})`, detail pretty JSON;
  - other dynamic → `use ${tool}`, detail pretty JSON.
  - With no item, keep today's generic title.
- Detail precedence: the item-derived detail wins over params.command for non-commandExecution items.

4) source-approval-card.jsx and .css: render the reason under a 'Reason' label (text-footnote label plus body, as in approval-current.js:15255-15285) with class names sac-reason / sac-reason-label.

5) README: describe grant scoping, extra roots auto-approval for file writes (bash escalations still prompt), and remove the zh/acceptForSession caveat that no longer applies.

## Findings (audit evidence)

### approvals-permissions-session-grant-overreach — "Allow for this session" grants are keyed wrongly: one file grant silently auto-approves later sandbox escalations (including danger-full-access and Plan-mode writes), while non-bash tool grants never match again [deepseek/high/M/both]
- User-visible: After one "Allow for this session" on a Manual-mode edit, a later write that escalates beyond the workspace runs with no card at all. So does any escalated write after switching to Plan. Conversely, "Allow for this session" on a subagent or MCP call has no effect on the next call with different arguments.
- Evidence: harness/packages/codex-app-server/src/index.js:300-304 gives every fileChange approval grantKey 'files'. :305-312 keys commands on the exact `command:<string>`, where a non-bash command is `${toolName} ${JSON.stringify(args)}`. :314 checks grants before asking and also checks `tool:${toolName}`, which nothing ever adds (dead code). :335-338 acceptForSession stores the key. The key ignores where the ask came from: the bridge's own Ask-mode ask (index.js:279-285) and a Harness sandbox escalation (dsh-sandbox/lib/index.js:105-113, reason `escalate sandbox to ${mode}`) share the same key, and the requested mode (workspace-write vs danger-full-access) is ignored. sessionGrants (index.js:79) are never cleared when the mode changes (applyPermissions index.js:417-432). Original: no standing grant is offered for out-of-project file access (approval-current.js:14340-14354, disableAlwaysAllow and "This file is outside your project folder"), and persistent allow is tool-scoped, "Don’t ask again for this tool" (approval-current.js:15820-15826).
- Fix: Move the approval mapping into a pure harness/packages/codex-app-server/src/approval.js. Record on the LiveThread the callIds for which the bridge's own pre-execute returned 'ask'; any other approval request is a sandbox escalation. Grant keys: Ask-mode asks -> 'ask:file' (write/edit), 'ask:command:<cmd>' (bash), 'ask:tool:<name>' (all other tools, matching the source's per-tool always-allow). Escalations -> 'escalate:<mode>:command:<cmd>' / 'escalate:<mode>:file:<abs path>'. Never grant danger-full-access file escalations for the session: send params.sessionGrantable=false and have app/src/approval-card-model.mjs drop the acceptForSession action when it is false. Clear the escalation grants in applyPermissions whenever the effective preset changes.
- Files: harness/packages/codex-app-server/src/index.js, harness/packages/codex-app-server/src/approval.js, app/src/approval-card-model.mjs
- Verification: New harness/tests/approval.test.mjs: table tests on grantKeyFor({origin, toolName, item, mode}). A 'files' Ask grant must not match an escalation; a tool grant matches the same tool with different args; escalation grants are dropped after a preset change (cd harness && node --test tests/approval.test.mjs). Extend app/tests/approval-card-model.test.mjs: sessionGrantable:false leaves only Deny / Allow once (cd app && node --test tests/approval-card-model.test.mjs).

### approvals-permissions-reason-text — Approval reason shows Chinese escalation text in the English card, Manual-mode cards add a synthetic "Ask permissions mode is on." line, and the reason lacks the source's labelled Reason block [deepseek/medium/S/both]
- User-visible: Auto and Plan escalation cards show text like "允许本次操作使用 danger-full-access 权限：…" in an English card. Every Manual-mode card has an extra "Ask permissions mode is on." line that Claude never shows.
- Evidence: harness/packages/codex-app-server/src/index.js:298 picks reason = displayReason.zh ?? displayReason.en ?? reason; dsh-sandbox/lib/index.js:109-113 supplies both en ("Allow this operation with ${mode} permissions: …") and zh; index.js:283 Ask-mode ask sets displayReason {en:'Ask permissions mode is on.'}. App: app/src/approval-card-model.mjs:42 adds the reason as generic context; app/src/source-approval-card.jsx:223 renders it as a plain <p class=sac-context>. Original: approval-current.js:14636-14646 (nM/tM) strips known reason ledes; :15255-15285 renders the description under a "Description" label and the decision reason under a "Reason" labelled block.
- Fix: Bridge askClient: prefer displayReason.en, strip the "Allow this operation with <mode> permissions: " lede, and send the justification as reason, with the requested mode in the text (e.g. "Needs danger-full-access: <justification>"). Send reason:null for the bridge's own Ask-mode asks. App: give reason its own model slot in approval-card-model.mjs and render it in source-approval-card.jsx under a "Reason" label, styled like the source block (text-footnote label + body).
- Files: harness/packages/codex-app-server/src/index.js, harness/packages/codex-app-server/src/approval.js, app/src/approval-card-model.mjs, app/src/source-approval-card.jsx, app/src/source-approval-card.css
- Verification: harness/tests/approval.test.mjs reasonFor(): an escalation with en+zh yields the English justification without the lede, and an Ask-mode ask yields null. app/tests/approval-card-model.test.mjs: reason goes to its own slot, not the context list. app/tests/source-shortcut.test.mjs SSR: the card contains a "Reason" label (cd app && node --test tests/approval-card-model.test.mjs tests/source-shortcut.test.mjs).

### approvals-permissions-additional-folders — Session additional folders are dropped by the bridge: writes there trigger danger-full-access escalation prompts instead of being writable [deepseek/low/S/harness]
- User-visible: After "Add folder" in Auto mode, a write into that folder is first denied by the sandbox. DeepSeek then asks for a full-access escalation card, where Codex treated the folder as a writable root.
- Evidence: app/electron/permission-policy.mjs:14 sends writableRoots [cwd, ...additionalFolders]; app/src/main.jsx:1144 (turn params) and :1206 (tells the model about the folders). The bridge reads only sandboxPolicy.type (harness/packages/codex-app-server/src/index.js:419), and Harness workspace-write has a single root, the session cwd (node_modules/@deepseek-ai/dsh-sandbox-policy/lib/index.js:135-145).
- Fix: Store sandboxPolicy.writableRoots on thread.permission in applyPermissions. In the approval/request handler, auto-return 'allowed-once' when the request is a write/edit escalation whose absolute file_path (from projector.tools args) lies inside a client-declared writable root; bash escalations still prompt. Document this in harness/README.md under the known limitations.
- Files: harness/packages/codex-app-server/src/index.js, harness/packages/codex-app-server/src/approval.js, harness/README.md
- Verification: harness/tests/approval.test.mjs insideWritableRoots(): a path inside an extra root returns true; a path outside, ../ traversal, and a sibling-prefix path ('/a/bc' vs '/a/b') return false; bash escalations are never auto-approved (cd harness && node --test tests/approval.test.mjs).

### composer-models-additional-folders — Folders from 'Add another folder' and /add-dir are sent as writable roots, but the DeepSeek sandbox drops them [deepseek/medium/M/both]
- User-visible: Folders added from the composer context row or with /add-dir show as chips and are announced to the model as workspace directories. DeepSeek's workspace-write sandbox only allows writes under the session cwd, so writes and edits in the extra folder come back as '[sandbox: file access denied under workspace-write mode]' and need an escalation each time. The UI doesn't mention this.
- Evidence: App: app/src/source-composer.jsx:351-361 renders the extra-folder chips and the Add another folder button; app/src/main.jsx:1205-1206 adds the 'Additional workspace directories' text; app/electron/permission-policy.mjs:10-14 sends sandboxPolicy.writableRoots [cwd, ...additionalFolders]. Bridge: harness/packages/codex-app-server/src/index.js:417-432 applyPermissions reads only sandboxPolicy.type (POLICY_SANDBOX at :41), so writableRoots is discarded. Harness: dsh-sandbox/lib/types/index.d.ts:27-31 has a single workspaceRoot per execution policy, and dsh-fs-sandbox/README.md:12,46 says workspace-write allows only the workspace root and temp, returning FS_SANDBOX_DENIED with an escalation hint.
- Fix: In applyPermissions, store thread.permission.extraRoots as the realpath of writableRoots minus cwd. In askClient (index.js:293-352), return 'allowed-once' for fileChange approvals whose target paths all canonicalize under cwd or an extra root; bash escalations still prompt. Put the containment check in a pure src/roots.js. Record the remaining limitation (bash writes outside cwd still ask) in harness/README.md.
- Files: harness/packages/codex-app-server/src/index.js, harness/packages/codex-app-server/src/roots.js, harness/tests/roots.test.mjs, harness/README.md
- Verification: cd harness && node --test tests/roots.test.mjs: withinRoots('/x/extra/a.txt', ['/x/extra']) is true; '/x/extra2/a' and '/x/extra/../etc' are false; the approval helper returns 'allowed-once' for a write under an extra root and 'ask' for a bash command. The end-to-end Harness flow (denial, escalation, approval/request) is inferred from the fs-sandbox README and needs one live run to confirm.

### approvals-permissions-tool-verb-titles — Command approvals for non-bash tools read "Allow DeepSeek to run this command?" over a one-line "toolname {json}", and bash ignores its description; the source's per-tool verbs are now feasible from item data [fidelity/medium/M/both]
- User-visible: A Manual-mode subagent, workflow, send_message or MCP call shows "Allow DeepSeek to run this command?" with an unreadable single-line JSON blob. Bash cards never show the model's description in the title, unlike Claude's "Allow Claude to run <description>?".
- Evidence: Local: app/src/approval-card-model.mjs:55-59,73-77: command approvals always get the generic title, with detail = params.command (which takes precedence over item). harness/packages/codex-app-server/src/index.js:305 builds a non-bash command as `${toolName} ${JSON.stringify(args)}`. projection.js:116 keeps args.description on commandExecution, and projection.js:166-175 gives mcpToolCall {server, tool, arguments} and dynamicToolCall {tool, arguments}, which the card already receives as `item` (app/src/main.jsx:2196 items.find by itemId). Original: approval-current.js:14508-14595 maps Bash to "run" + meta description + command detail (clampTitle), Task/Agent to "run an agent" + description, Skill to "run skill /name", WebFetch to "fetch <url>", WebSearch to "search the web", and anything else to "use {label}" + pretty JSON detail. HANDOFF.md:111 lists these verbs as an open gap because Codex lacked the data.
- Fix: In approvalCardModel(request, item), derive the heading from the item when present. dynamicToolCall subagent/subagent_fork -> {action:'run an agent', meta: arguments.description}; skill -> 'run skill' '/name'; other tools -> {action:`use ${tool}`} with detail JSON.stringify(arguments, null, 2). mcpToolCall -> 'use {tool} ({server})' with JSON detail. commandExecution with item.description -> {action:'run', meta: description}, command as detail, clampTitle. Keep the generic title only when no item is found. Optionally, have the bridge stop stuffing JSON into params.command for non-bash tools (send null and let the item drive the card).
- Files: app/src/approval-card-model.mjs, app/src/source-approval-card.jsx, harness/packages/codex-app-server/src/index.js
- Verification: app/tests/approval-card-model.test.mjs new cases: dynamicToolCall subagent -> "Allow DeepSeek to run an agent <description>?" with pretty JSON detail; mcpToolCall -> "use tool (server)"; bash item with description -> heading run/description with the command detail; no item -> unchanged generic title. SSR in app/tests/source-shortcut.test.mjs checks the two .sac-em spans (cd app && node --test tests/approval-card-model.test.mjs tests/source-shortcut.test.mjs).
