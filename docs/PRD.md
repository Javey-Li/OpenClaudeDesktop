# PRD：Claude Desktop 日常替代应用

状态：草案，2026-10-26。本文定义产品目标与完成条件，不代表功能已经实现。当前事实看根目录 [README](../README.zh-CN.md)，施工入口看 [开发说明](DEVELOPMENT.md)。

## 产品是什么

这是基于 OpenClaudeDesktop 继续开发的桌面应用。以选定版本的官方 Claude Desktop 为行为参考，逐步提供完整的日常使用流程。复用上游已经实现的宿主、界面、Agent 桥和工具，补齐真实使用中的缺口。

本项目首先服务维护者个人。用户需要在同一处开始对话、使用资料、生成和修改产物，并让 Agent 执行文件、代码及其他工作任务。重新打开应用时，仍能理解之前做到了哪里、哪些操作已执行、哪些还需要自己决定。

## 要解决的问题

1. 单有聊天界面，不能完成资料、产物和任务之间的连续工作。
2. 工具、内核和模型的能力不同，但界面容易把“显示出来”误当成“确实执行”。
3. 中断、失败或重新启动后，任务与文件状态需要可追溯，不能无声丢失或重复执行。
4. 接入方式、账号权益与运行位置需要清楚。用户应知道数据去了哪里、任务在哪里跑、费用属于哪条路径。

## 核心使用流程

| 流程 | 用户需要得到什么 |
|---|---|
| 带资料继续对话 | 找到历史，添加图片或文档，编辑或重试消息，保留清楚的上下文与分支 |
| 围绕项目长期工作 | 同一项目共享指令与资料，跨会话引用；资料更新和删除后不会继续使用过期内容 |
| 生成并持续修改产物 | 从对话产生 Artifact 或文件，查看、编辑、比较版本、回退、运行和导出 |
| 委托多步任务 | 选择工作范围，查看计划与进度，批准或拒绝操作，途中纠偏、中断和恢复 |
| 下次接着做 | 重启或换设备后明确知道任务状态；云任务与本机任务的可继续条件分别说明 |

## 完整功能范围

| 领域 | 产品要求 | 判断完成的代表场景 |
|---|---|---|
| 聊天与上下文 | 流式回复、历史与搜索、编辑、重试、分支、附件沿用、停止、上下文整理、记忆控制 | 编辑早期消息仍保留旧分支；失败可恢复；删除的历史或记忆不继续被引用 |
| Projects | 创建、修改、归档、项目指令、资料管理、检索引用、跨会话使用，以及参考版本中适用的项目组织能力 | 两个会话使用同一项目资料；更新和删除后引用正确；项目之间不串资料 |
| 附件与文档 | 图片、PDF、Office、表格和文本的摄入、解析、引用与错误反馈；文档生成和下载 | 图文 PDF 与表格内容确实进入任务；损坏、超限和不支持类型有明确结果 |
| Artifacts | 识别、预览、连续修改、直接编辑、版本、回退、运行与导出；覆盖参考版本中的文档、幻灯片和设计等产物 | 连续修改后各版可重开；预览、源码、导出对应同一版；运行环境不取得宿主密钥 |
| Code 与工作任务 | 文件、终端、代码改动、差异、worktree、预览、计划、多步执行、队列、后台与定时任务 | 批准后真实改动；拒绝无副作用；并行任务不误写工作区；恢复不盲目重放已执行操作 |
| 工具与扩展 | Skills、MCP、插件、连接器、快捷命令与相关审批 | 安装和启停实际生效；断连可解释；撤销授权后不能继续调用 |
| 浏览器与桌面 | 导航、页面读取、输入、截图、文件传递与标签页；参考版本中存在的 OS 操作 | 浏览器与 OS 能力分别授权；取消和失焦不导致继续误操作；会话不串标签页 |
| 系统体验 | 设置、快捷键、窗口、通知、语音、输入法、滚动、焦点、动画与无障碍 | 键盘可完成主要流程；重启、多窗、缩放和减少动画设置行为正确 |
| 云端与同步 | 持久远程任务、跨端继续、同步、离线状态，以及需要的本机在线桥 | 本机关机后可继续的云任务仍执行；无法访问本机时明确等待；同步冲突和删除可解释 |
| 安装与维护 | 可重建、资源来源、数据迁移、备份恢复、升级与回退 | 干净环境按文档可构建；升级失败可恢复；不依赖未说明的私人目录 |

最终范围保持完整。分阶段只决定实现顺序；暂缺功能仍留在需求中，不能因为难做或依赖服务端就从目标移除。

## 必须贯穿所有功能的规则

- UI 状态来自真实执行结果。工具拒绝、失败、取消与成功分别显示。
- 数据、上下文、文件修改和任务状态都有明确归属。会话回退与文件回退分别处理。
- 模型能力、应用功能和账号权益分别说明。某种接入不自动获得官方服务端功能。
- 按需授权读写、执行、站点、桌面应用和连接器；保持用户可理解的操作范围。
- 官方客户端用于研究行为，不假设可以恢复未提供的服务端代码。缺少授权接口时说明替代实现与体验差异。
- 保留来源与许可。继承代码、参考组件、提取资源和本项目新增代码分别追踪。

## 原版参考与能力状态

每个涉及原版的结论记录客户端版本、OS、账号可见功能和观察日期。客户端版本号不能单独固定云端功能或灰度状态。没有运行验证的行为写“未验证”。

每项功能以四种信息追踪：需求、已有实现、通过的具体场景、剩余差距。可以确认一个场景通过，不据此把整个领域标成完成。截图、静态源码、mock、单元测试、真实模型和完整 GUI 运行各有范围，不互相替代。

## 开发顺序

1. 让现有源码可独立构建并启动，清楚记录上游基线和资源来源。
2. 贯通一个真实的会话—工具—审批—结果—持久化流程，再验证编辑、中断和恢复。
3. 补齐项目资料、附件与 Artifact 版本，把长期工作流程连起来。
4. 扩展 Code、工作任务、工具、浏览器与 OS 能力，逐项补齐系统交互。
5. 完成云执行、同步和服务连接，并以完整日常流程检查各项差距。

这些是可验证的阶段，不是发行日期或“完全一致”的承诺。没有通过构建和真实运行前，不给出可用版本或确定工期的宣传。

## 尚待确认

- 选定哪个官方版本和账号实际界面作为首轮完整行为参考。
- 各内核目前能完成哪些真实任务，哪些只能显示界面或返回部分结果。
- 缺失资源如何以来源明确的实现补齐，哪些提取内容需要替换。
- 官方服务有哪些授权接口，哪些能力需要独立运行环境或后端。

这些问题先用代码、运行与小型行为场景回答。只把影响当前阶段的未决问题变成开发任务，不预先创建庞大的框架或文档体系。
